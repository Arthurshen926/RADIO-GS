# Expanded-source teatime rebuild: memory recovery

This records an execution repair, not a retrieval improvement claim. Geometry, the 23 training frames, original validation frames 64/115, model dimensions, supervision, and 35,856 training steps remain unchanged. Official evaluations are handled separately after reconstruction.

The first training attempt exhausted GPU memory inside Adam's foreach denominator allocation (494 MiB). Sequential Adam alone still exhausted memory while creating the same full-parameter denominator. Chunking the upstream single-tensor Adam function passed the first optimization step, but a subsequent SAM gradient diagnostic required another 494 MiB and failed. These attempts demonstrate that optimizer temporaries were only one part of the peak, not the sole underlying cause.

The retained repair instead moves only frozen dense teacher caches to CPU after exactly the original GPU interpolation. Each training access selects the same rows and restores them to the original GPU. The original Adam implementation, parameters, losses, sampling sequence, and gradient diagnostics remain intact. The isolated launcher binds the original training source SHA-256 and replaces one dense-cache construction expression at runtime; it does not alter frozen source files.

Actual input teacher tensors are RADIO [25, 1280, 46, 62] and DINO [25, 768, 46, 62]. Their interpolated 96×128 float32 caches occupy 2,516,582,400 bytes (2.34375 GiB). The storage audit is `output/full_field_rebuild_next19/teatime/dense_cpu_storage.json`. A GPU comparison of 1,024 selected rows is bitwise equal (`dense_cpu_verification.json`). Training passed step 2,130 after this change. The first measured steady interval was 600 steps in 71 seconds, approximately 8.45 steps/s; total completion and final results are not claimed by this interim note.

Failed attempts, empty partial output directories, logs, and recovery receipts are retained under the new teatime output root. An Adam-moment CPU-offload attempt was stopped before training because it would transfer much more data per step than teacher-row selection; it was not used for the retained model.

The original recovery supervisor was replaced without interrupting training PID 2457979 so waldo could rebuild concurrently on GPU5. The adopted watcher runs only the remaining teatime stages. Its receipt explicitly records that the orphaned training process exit code cannot be recovered via `wait`; completion requires the final report, absence of a traceback, and output hashes. Subsequent child stages retain normal exit-code checks.

## Completion

The complete 35,856-step initial reconstruction and all subsequent pixel evidence, source extent, rendered extent, semantic transfer, calibration, admission, text/reference online and replay stages finished. `execution.json` is complete, source acceptance is true, and promotion remains false. Online/replay run dictionaries agree exactly. The final text route diagnostic reports 59 observations, observation mIoU 60.32%, category-macro mIoU 53.68%, AP 79.40%; these are the runner's query-route diagnostics, not a substitute for the separately scheduled official native-grid comparison.

A second memory limit occurred in grounded semantic transfer: the full [4127, 1347420] fp16 source probability table was expanded into a 22,243,209,360-byte float32 GPU tensor, leaving insufficient space for the weighted design matrix. An isolated SHA-bound launcher now keeps that frozen table on CPU and copies exactly the requested row, preserving the original full matrix multiplication and closed-form solve. First/middle/last actual rows compare bitwise equal (`grounded_cpu_verification.json`). Multi-region union lifting is unchanged. All 4,127 source proposals remain. The successful expensive image calibration was reused with its output hashes; failed-stage evidence remains in `failed_pixel_grounded_probability_oom`.

The adopted process's base receipt was corrected to `returncode: null`, explicitly recording unavailable exit status and complete-step/report/model-hash evidence. Before/after receipts and hashes are retained in `receipt_metadata_correction/correction.json`; the top-level dependency hashes were updated consistently. No model weights were modified by this correction. The official evaluation agent was notified only after correction, avoiding a sealing race.

The final implementation differs from the frozen recipe only in these two temporary-memory storage choices; task counts, source/validation split, geometry, model architecture, original Adam, all loss functions, optimization budget, scope choices, and evaluation routes are unchanged. These execution fixes are not evidence that the source expansion improves retrieval; official comparisons determine that separately.
